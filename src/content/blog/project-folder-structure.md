업무 파일이 많아질수록 사람들은 폴더를 더 세분화하려고 합니다. 하지만 폴더 단계가 깊어질수록 오히려 어디에 넣었는지 기억하기 어려워지고, 같은 파일이 여러 곳에 복사되기 쉽습니다.

좋은 업무 폴더 구조는 세밀한 분류보다 **누가 봐도 파일의 현재 상태와 위치를 빠르게 이해할 수 있는 단순한 구조**에 가깝습니다. 프로젝트마다 같은 뼈대를 반복하고, 파일명 규칙을 함께 맞추면 검색과 인수인계도 쉬워집니다.

## 최상위 폴더는 업무 단위로 나눈다

가장 위 단계에서는 프로젝트, 고객, 팀처럼 실제 업무 단위를 기준으로 나누는 것이 좋습니다.

예를 들어 다음처럼 시작할 수 있습니다.

- project-alpha
- project-beta
- team-shared
- archive

최상위 폴더부터 문서 종류별로 쪼개면 같은 프로젝트 자료가 여러 곳에 흩어질 수 있습니다. 프로젝트를 기준으로 묶으면 관련 문서, 회의록, 시안, 결과물을 한 흐름에서 찾기 쉽습니다.

## 프로젝트 안에서는 세 단계면 대부분 충분하다

폴더를 지나치게 세분화하기보다 프로젝트 안에서 다음 세 가지 정도로 나누면 관리하기 쉽습니다.

1. work-in-progress
2. shared
3. final

work-in-progress에는 작업 중인 초안과 편집 파일을 둡니다. shared에는 검토나 협업을 위해 공유하는 파일을 두고, final에는 승인되었거나 최종 배포에 쓰는 결과물을 넣습니다.

팀 성격에 따라 폴더 이름은 달라질 수 있지만 핵심은 **진행 상태를 폴더만 봐도 알 수 있게 만드는 것**입니다.

## 문서 종류 폴더는 필요할 때만 만든다

회의록, 견적서, 보고서, 디자인 파일이 많다고 해서 처음부터 각각 별도 폴더를 만들 필요는 없습니다.

파일이 많지 않다면 같은 폴더 안에서 파일명으로 구분하는 편이 더 빠를 수 있습니다. 예를 들어 날짜와 문서 종류가 포함된 파일명 규칙을 쓰면 폴더 수를 늘리지 않아도 정렬과 검색이 가능합니다.

파일명이 제각각이라 찾기 어렵다면 먼저 [업무 파일명 규칙](/blog/work-file-naming-rules/)을 정한 뒤 폴더 구조를 손보는 것이 좋습니다.

문서 종류별 폴더는 한 폴더 안에 파일이 너무 많아져 실제 탐색이 불편해졌을 때 추가하면 충분합니다.

## 개인 작업과 팀 공유 파일을 섞지 않는다

공유 폴더 안에 개인 메모와 임시 파일까지 모두 넣으면 다른 사람이 무엇을 써야 하는지 헷갈릴 수 있습니다.

개인 작업 초안은 개인 작업 공간에 두고, 팀에서 실제로 검토하거나 사용할 파일만 shared 폴더로 옮기는 방식을 권장합니다.

이렇게 하면 공유 폴더가 일종의 배포 공간 역할을 하게 됩니다. 다른 사람은 모든 작업 과정을 볼 필요 없이 현재 검토 대상만 확인할 수 있습니다.

## 최종 파일은 하나의 위치만 정한다

같은 결과물을 final, 제출용, 고객전달, 완료 같은 여러 폴더에 복사해두면 어느 파일이 진짜 최신인지 다시 확인해야 합니다.

최종본의 공식 위치를 한 곳으로 정하고, 다른 곳에서는 가능하면 복사본을 늘리지 않는 편이 좋습니다.

예를 들어 final 폴더에 승인된 파일만 넣기로 했다면, shared 폴더에 남아 있는 이전 검토본은 파일명에 review 상태를 유지해 구분할 수 있습니다.

중요한 것은 폴더 이름보다 **최종본을 어디에서 찾는지 팀이 하나의 규칙으로 알고 있는 것**입니다.

## 날짜 폴더는 반복 업무에만 쓴다

모든 프로젝트를 연도·월·일 폴더로 나누면 단계가 너무 깊어질 수 있습니다.

날짜 폴더는 매일 생성되는 보고서, 정기 백업, 촬영 원본처럼 시간 순서 자체가 중요한 자료에 적합합니다.

반대로 하나의 프로젝트에서 문서가 여러 번 수정되는 형태라면 프로젝트 폴더 안에서 파일명에 날짜나 버전을 붙이는 편이 더 찾기 쉬운 경우가 많습니다.

예를 들어 아래 두 방식은 용도가 다릅니다.

- 반복 보고서: 2026 / 09 / daily-report
- 프로젝트 문서: project-alpha / shared / 2026-09-28_proposal_v03.pdf

폴더와 파일명 중 어느 쪽에 날짜를 둘지는 실제로 어떻게 검색하는지에 맞춰 정하면 됩니다.

## 완료 프로젝트는 작업 공간에서 분리한다

진행 중인 프로젝트와 몇 년 전 끝난 프로젝트가 같은 위치에 계속 쌓이면 폴더 목록이 길어집니다.

완료된 프로젝트는 archive 폴더로 옮기고, 현재 진행 중인 프로젝트만 상위에서 바로 보이게 유지하는 편이 좋습니다.

다만 보관한다고 해서 폴더 구조나 파일명을 다시 전부 바꿀 필요는 없습니다. 기존 구조를 유지한 채 위치만 archive로 옮기면 나중에 찾을 때도 혼란이 적습니다.

## 폴더 깊이는 가능한 한 얕게 유지한다

파일 하나를 열기 위해 다섯 번, 여섯 번 폴더를 들어가야 한다면 구조가 지나치게 세분화됐을 가능성이 큽니다.

다음과 같은 구조면 대부분의 소규모 프로젝트에서 충분합니다.

project-alpha  
→ work-in-progress  
→ shared  
→ final

세부 문서 분류가 정말 필요한 경우에만 한 단계를 추가하세요. 폴더를 미리 많이 만들어두면 실제로 사용하지 않는 빈 폴더가 늘고, 사람마다 다른 위치에 파일을 넣게 됩니다.

## 팀에서 규칙을 정할 때는 예시를 같이 남긴다

“폴더를 잘 정리해 주세요”라는 문장만으로는 사람마다 다른 구조를 만들게 됩니다.

대신 실제 예시 하나를 보여주는 것이 좋습니다.

project-alpha  
- work-in-progress  
- shared  
- final  
- references

그리고 각 폴더에 무엇을 넣는지 한 줄씩 설명하면 됩니다.

- work-in-progress: 개인·팀 작업 중인 파일
- shared: 검토와 협업에 사용할 파일
- final: 승인 또는 배포된 결과물
- references: 원본 자료와 참고 파일

규칙이 복잡해질수록 지키기 어렵습니다. 새 팀원이 설명 없이도 이해할 수 있을 정도로 단순해야 오래 유지됩니다.

## 이미 폴더가 엉켜 있다면 오늘부터 새 규칙을 적용한다

오래된 공유 폴더를 한 번에 전부 재정리하면 기존 링크가 깨지거나 다른 사람이 파일을 찾지 못할 수 있습니다.

이럴 때는 현재 진행 중인 프로젝트부터 새 구조를 적용하고, 과거 자료는 자주 사용하는 것만 천천히 옮기는 편이 안전합니다.

특히 클라우드 문서나 협업 도구에서 링크로 참조되는 파일은 위치를 바꾸기 전에 영향을 확인해야 합니다.

## 가장 중요한 기준은 찾는 시간이 줄어드는가다

좋은 폴더 구조는 보기 좋은 구조가 아니라 실제 업무 시간을 줄여주는 구조입니다.

프로젝트별로 같은 뼈대를 사용하고, 작업 중·공유·최종 상태를 분리하고, 완료 프로젝트를 archive로 옮기면 대부분의 혼란을 줄일 수 있습니다.

여기에 [회의록에서 결정사항과 할 일을 정리하는 방법](/blog/meeting-notes-action-items/)처럼 문서 내용 자체의 구조까지 맞추면 파일을 찾은 뒤 다시 내용을 해석하는 시간도 줄어듭니다.

폴더를 더 많이 만드는 것보다 **파일이 어디에 있어야 하는지 누구나 예측할 수 있게 만드는 것**이 업무 폴더 정리의 핵심입니다.
