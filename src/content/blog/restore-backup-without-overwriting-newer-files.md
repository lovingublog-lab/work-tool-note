업무 폴더에서 파일이 사라져 백업을 찾았다고 해도, **백업 폴더 전체를 현재 작업 공간에 덮어쓰는 것은 마지막 선택지**여야 합니다. 백업은 특정 시점의 사본이므로 그 이후 수정된 정상 파일까지 이전 상태로 되돌릴 수 있습니다. 파일을 찾았다는 안도감 때문에 '모두 교체'를 누르기 전에, 복구 대상과 보존해야 할 현재 상태를 구분해야 합니다.

예를 들어 목요일에 작성한 보고서가 금요일 오전에 삭제됐다고 가정해 봅니다. 수요일 밤 백업에는 보고서의 이전 버전만 있을 수 있습니다. 해당 보고서만 복원하는 것이 목적이라면 금요일까지 팀원이 수정한 다른 문서들을 수요일 상태로 되돌릴 이유는 없습니다.

## 복구 목표가 파일 하나인지 폴더 전체인지

복원 작업 전에 사고 범위를 한 문장으로 적어보세요.

| 실제 문제 | 복구 대상 | 주의할 점 |
| --- | --- | --- |
| 보고서 한 개가 삭제됨 | 해당 파일의 복원 가능한 사본 | 같은 이름의 최신 파일이 다른 위치에 있는지 확인 |
| 폴더 일부가 잘못 이동됨 | 원래 경로와 누락된 하위 항목 | 이동된 파일을 중복 복원하지 않음 |
| 여러 파일이 잘못 수정됨 | 영향을 받은 파일의 특정 이전 버전 | 정상 변경까지 이전 버전으로 되돌리지 않음 |
| 작업 공간 전체가 손상됨 | 시스템·저장소 담당자가 정한 복구 범위 | 권한·연결·자동 동기화와 업무 중단 영향 검토 |

전체 폴더를 복원할지 고민되는 상황이라면 **영향받지 않은 파일을 보호할 방법**부터 정해야 합니다. 복원은 삭제된 파일을 되찾는 일일 수도 있지만, 정상 파일을 이전 버전으로 바꾸는 위험도 함께 갖고 있습니다.

## 기준본과 백업본을 같은 위치에 열어 놓지 않는다

작업을 시작할 때는 세 가지 위치를 구분하면 혼선이 줄어듭니다.

- **현재 기준본:** 팀이 정상적으로 작업·공유하는 원래 폴더입니다. 가능한 한 수정하지 않고 현재 상태를 확인합니다.
- **백업 원본:** 삭제 전 시점의 저장본입니다. 검증 전에는 직접 수정하지 않습니다.
- **복구 검토본:** 백업에서 별도의 임시 공간으로 가져온 후보 파일입니다. 복원할지 비교하는 데만 씁니다.

예를 들어 프로젝트 폴더가 Project-A라면 복구 검토본은 실제 협업 폴더 밖의 승인된 작업 공간에 Project-A_restore-review_2026-11-06 같은 이름으로 둡니다. 날짜는 실행 시점을 설명할 뿐, 복구본이 가장 최신이라는 의미가 아닙니다.

팀의 보안·보존 정책이 적용되는 자료라면 임시 공간도 허용된 저장소에서 선택해야 합니다. 개인 클라우드나 개인 외장하드로 파일을 빼서 비교하는 방식은 허가 없이 사용하지 않습니다.

## 수정 시각만으로 최신 내용을 결정하지 않는 이유

파일 속성의 수정 날짜가 뒤라 해도 그 파일이 정답인 것은 아닙니다. 백업을 복사하는 과정에서 시각이 바뀔 수 있고, 오래된 내용을 다시 저장했을 수도 있습니다. 같은 파일명의 후보가 두 개라면 비교 기준을 세 단계로 나눕니다.

**① 업무상 기준:** 어느 보고 기간과 어느 고객·프로젝트를 위한 문서인지 확인합니다. 제목만 같은 다른 과제의 파일일 수 있습니다.

**② 내용상 차이:** 표의 합계, 마지막 승인 문구, 대표 항목, 시트 수 등 해당 문서의 핵심 변경점을 비교합니다. 큰 파일이라면 변경 내역이나 문서 비교 기능을 사용할 수 있지만, 자동 비교 결과를 그대로 승인하지 않습니다.

**③ 확인 주체:** 팀이 합의한 최신 결정을 반영하는지 담당자 또는 승인권자에게 확인합니다. 최종본이 어느 위치에 있어야 하는지도 함께 정합니다.

예컨대 백업본의 파일명이 제안서_final.docx이고 현재 파일명이 제안서_v05.docx여도, 이름만으로 오래된 파일을 최신본 위에 올려놓을 수 없습니다. 이런 혼란을 예방하는 기준은 [문서 버전 관리의 기본 규칙](/blog/document-version-management/)과 연결됩니다.

## 파일 하나를 복원하는 실제 작업 흐름

복원 권한이 있고 파일 손상·보안 사고가 아닌 일반적인 실수로 확인된 경우, 다음 흐름을 적용할 수 있습니다.

1. **현재 경로를 기록합니다.** 누락된 위치, 파일명, 마지막으로 정상 확인한 시각, 담당자를 적습니다.
2. **현재 폴더 상태를 보존합니다.** 여러 사람이 동시에 편집 중이라면 담당자에게 상황을 알려 추가 덮어쓰기 가능성을 줄입니다.
3. **백업 시점을 확인합니다.** 백업의 날짜뿐 아니라 복구하려는 내용이 존재하는지 미리보기나 별도 사본으로 검토합니다.
4. **임시 공간으로 복구합니다.** 원래 경로에 곧바로 덮어쓰지 않고 비교용 위치에 파일을 가져옵니다.
5. **차이를 확인하고 복원 범위를 결정합니다.** 현재 파일이 존재하면 둘 다 보존한 상태에서 어떤 버전을 사용할지 확정합니다.
6. **허용된 방식으로 기준본을 갱신합니다.** 담당자와 경로가 확정된 뒤 승인된 복원 방법을 따르고, 필요한 경우 교체 전 상태도 보존합니다.
7. **열어서 결과를 검증합니다.** 파일 이름이 나타나는지뿐 아니라 내용과 권한, 참조 링크, 최종 사용자가 여는 위치까지 확인합니다.

프로그램마다 이전 버전 복원·휴지통 복원·백업 불러오기 기능의 명칭과 덮어쓰기 동작이 다릅니다. 이 절차는 특정 버튼을 누르는 순서가 아니라 **복원 범위를 안전하게 결정하는 공통 작업 흐름**입니다.

## 복원됐는데 팀에서는 여전히 옛 파일이 보일 때

파일 하나를 원래 위치에 되살렸는데 다른 팀원이 오래된 내용을 본다면 세 가지를 확인해야 합니다. 첫째, 파일을 연 경로가 같은지. 둘째, 공유 링크가 복원 전 파일의 식별자에 연결돼 있지는 않은지. 셋째, 동기화나 오프라인 사본으로 인해 이전 상태를 열고 있지는 않은지입니다.

복원본이 성공적으로 열리더라도 공유 경로가 달라지면 현업에서는 '아직 복구되지 않았다'고 느낄 수 있습니다. 따라서 팀원이 평소 쓰는 링크나 폴더에서 파일을 열어 보는 확인이 필요합니다. 중요한 문서일수록 **복구한 파일의 이름·경로·버전·담당자·확인 시각**을 짧게 남깁니다.

[프로젝트별 폴더 구조를 단순하게 정리하는 방법](/blog/project-folder-structure/)을 참고해 작업 중·공유·최종 공간을 분리해 두었다면, 복원 후 기준본을 정할 때도 혼란이 줄어듭니다.

## 멈춰야 하는 사고와 복구를 끝내는 조건

랜섬웨어 의심, 악성 파일, 접근권한 탈취, 대량 삭제처럼 보안 사고 가능성이 있다면 임의 복원으로 덮어쓰지 말고 조직의 보안·IT 담당자에게 즉시 알립니다. 파일을 되살리는 행동이 원인 분석에 필요한 흔적을 바꾸거나 감염된 데이터를 다시 퍼뜨릴 수 있기 때문입니다. 보존기간이나 감사 대상 자료 역시 팀의 승인 절차를 따라야 합니다.

정상적인 백업 복원이 끝났다고 판단하려면 세 가지를 충족해야 합니다. **필요한 내용이 되살아났고, 그보다 최신인 정상 작업이 사라지지 않았으며, 담당자가 실제 사용 위치에서 결과를 확인했다**는 점입니다. 백업의 목적은 단순히 사본을 만드는 것이 아니라, 사고 뒤에 신뢰할 수 있는 업무 상태를 다시 확보하는 데 있습니다.
