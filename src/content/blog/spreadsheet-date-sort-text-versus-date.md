엑셀이나 스프레드시트에서 날짜 열을 오래된 순으로 정렬했는데 `2026-04-05`보다 `2026-01-20`이 아래에 남거나, 일부 행만 따로 모이는 경우가 있습니다. 표시된 모양을 모두 같은 날짜 형식으로 맞춰도 해결되지 않을 수 있습니다. **셀에 실제 날짜값이 들어 있는지, 날짜처럼 보이는 문자만 들어 있는지**가 정렬 결과를 가르기 때문입니다.

날짜가 들어온 경로부터 떠올려 보세요. 직접 입력한 값, 다른 파일에서 복사해 온 값, CSV에서 가져온 값이 한 열에 섞이면 겉으로는 같아도 저장된 데이터 종류가 다를 수 있습니다. 원본 표를 덮어쓰기 전에 별도 작업본에서 문제 행을 확인해야 합니다.

## 날짜 표시 형식과 셀 안의 값은 다르다

스프레드시트는 일반적으로 인식한 날짜를 내부 숫자 값으로 관리하고, 화면에서는 연-월-일 같은 형식으로 보여 줍니다. 반면 `2026.04.05`가 단순 텍스트로 들어왔다면 겉보기에 날짜여도 숫자 날짜처럼 계산·정렬되지 않을 수 있습니다.

날짜 열 전체를 선택해 표시 형식만 ‘날짜’로 바꿨다고 해서 텍스트가 언제나 자동으로 변환되는 것은 아닙니다. 표시 형식 변경은 **어떻게 보일지**에 관한 조치이고, 텍스트를 날짜값으로 바꾸는 일은 **무엇으로 인식할지**를 바꾸는 작업입니다.

예를 들어 같은 열에 다음처럼 입력됐다고 가정해 보겠습니다.

| 원래 보이는 값 | 확인할 문제 |
| --- | --- |
| 2026-04-05 | 실제 날짜값인지 텍스트인지 확인 |
| 2026. 4. 6 | 구분자와 공백을 포함한 텍스트일 가능성 |
| 04/07/2026 | 월·일 순서가 어느 지역 기준인지 확인 |
| 2026-04-08 오후 2:00 | 날짜만이 아니라 시간값이 포함됐는지 확인 |

문자열과 날짜값이 섞여 있으면 한 열을 정렬해도 기대한 시간 순서가 보장되지 않습니다. 빈칸, 잘못 인식한 날짜, 숨겨진 시간값도 함께 살필 필요가 있습니다.

## 문제 행만 골라 실제 날짜인지 판별한다

원본을 복사한 작업 시트에서 날짜 셀 옆에 확인용 열을 하나 만듭니다. 엑셀과 구글 스프레드시트에서는 `=ISNUMBER(A2)`처럼 셀의 값이 숫자로 저장돼 있는지 확인할 수 있습니다. 실제 날짜가 숫자 값으로 저장됐다면 참(TRUE)을 반환할 수 있고, 단순 문자열이라면 거짓(FALSE)으로 나타날 수 있습니다.

다만 이 함수 하나로 **올바른 날짜인지**까지 확인할 수는 없습니다. 단순 숫자도 참으로 판별되고, 날짜로 읽혔더라도 의도한 월·일이 뒤바뀌었을 수 있기 때문입니다. 숫자로 판별된 셀은 날짜 표시 형식을 적용해 연·월·일을 확인하고, 문자로 판별된 셀은 원래 입력값을 따로 보존합니다.

몇 개의 대표 행을 택해 다른 셀과 비교해 보세요. 정상 행, 뒤로 밀린 행, 복사해 온 행 각각 한두 건이면 원인이 모든 행에 있는지 특정 출처에만 있는지 판단하는 데 도움이 됩니다. 문제가 없는 행을 한꺼번에 다시 변환하지 않는 이유이기도 합니다.

## 날짜를 바꾸기 전에 월과 일이 뒤바뀌지 않았는가

`04/05/2026`은 지역에 따라 4월 5일로도, 5월 4일로도 해석될 수 있습니다. 자동 변환 결과가 날짜 형식으로 보인다는 이유만으로 정답이라고 볼 수 없습니다. 외부에서 받은 파일이라면 작성자나 데이터 설명서에서 날짜 순서를 확인하는 것이 우선입니다.

의미가 확정된 값에 한해서 원본 옆의 새 열로 변환합니다. 연·월·일이 각각 분리돼 있다면 `=DATE(2026,4,5)`처럼 날짜 구성요소를 명시하는 방식이 모호한 문자열 해석보다 안전할 수 있습니다. 단, 실제 데이터에서는 고정 숫자 대신 각 연·월·일 열을 참조하도록 설계해야 하며 잘못된 월·일 값은 별도로 검증해야 합니다.

CSV를 불러올 때 날짜 열의 형식이나 지역 설정을 확인할 수 있다면 가져오기 단계에서 올바르게 해석하도록 조정합니다. 이후 원본 텍스트와 변환 결과를 나란히 비교해 예상하지 못한 날짜가 생기지 않았는지 살펴보세요. 단순히 표기 기호 `/`를 `-`로 바꾸는 것만으로 지역별 의미까지 해결되지는 않습니다.

## 정렬이 맞아도 행의 관계가 깨지면 실패다

날짜 열만 선택해 정렬하면 옆의 고객명·금액·상태와 서로 다른 행으로 갈라질 수 있습니다. 날짜를 수정한 뒤에도 **기록 한 건을 이루는 전체 표 범위**를 함께 정렬해야 합니다. 특히 중간 빈 열, 병합 셀, 머리글, 숨겨진 행이 있다면 실제 데이터의 경계를 먼저 정합니다.

정렬 전에 원본 식별번호가 있다면 작업본에서 유지합니다. 수정 후에는 가장 이른 날짜, 가장 늦은 날짜, 문제가 있었던 대표 행 세 가지를 비교하고 그 행의 식별번호·금액·담당자가 원래대로 붙어 있는지 대조합니다. 이미 행이 섞인 것 같다면 임의로 역정렬하지 말고 원본에서 다시 작업하는 것이 안전합니다. 자세한 사고 방지 원칙은 [스프레드시트 정렬 후 행이 섞이지 않게 하는 기준](/blog/spreadsheet-sort-filter-row-integrity/)에서 확인할 수 있습니다.

정렬을 했는데도 날짜만 따로 움직인다면 날짜 형식 문제가 아닌 선택 범위 문제일 수 있습니다. 반대로 표 전체를 선택해도 일부 날짜가 엉뚱한 위치에 남는다면 값의 종류와 날짜 해석을 다시 점검합니다. 서로 다른 문제이므로 해결책을 섞지 않습니다.

## 반복 입력되는 표라면 수정 위치를 앞당긴다

이번에 날짜를 바로잡았더라도 다음 달에 같은 CSV를 붙여 넣으면 오류가 되풀이될 수 있습니다. 날짜값은 어떤 형식으로 받을지, 외부 파일의 월·일 순서가 무엇인지, 시간까지 포함할지, 입력 실패 시 빈칸과 오류 표시를 어떻게 다룰지 정해 두는 것이 좋습니다.

다른 사람이 입력하는 협업 표라면 날짜 열의 기준을 명시하고 가능하면 입력 검증을 적용합니다. [스프레드시트 입력 규칙을 열 단위로 정하는 방법](/blog/spreadsheet-input-rules-standardize/)처럼 입력 시점에서 형식을 통일하면 사후에 날짜를 대량 변환하는 작업을 줄일 수 있습니다.

날짜 정렬 오류의 해결 순서는 세 단계로 생각하면 됩니다. **원본 보존 → 실제 날짜값과 문자 날짜 구분 → 의미를 확인한 뒤 작업본에서 변환·전체 행 정렬.** 화면에 보이는 모양만 바꿔서는 해결되지 않던 이유도 이 순서에서 드러납니다.
